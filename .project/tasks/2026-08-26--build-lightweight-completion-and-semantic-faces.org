Implement Step 4 of the ~org-files-db.el~ rebuild.

* Planning

** Problem summary

Rust now returns prepared presentation rows, but Emacs cannot show them in completion yet.

Step 4 needs lightweight candidates that preserve Rust search and display text.

** Goals

- Build candidates directly from decoded presentation rows.
- Keep complete ~search_text~ in each completion candidate.
- Show Rust ~display_text~ without recalculating layout.
- Map semantic roles to configurable Emacs faces.
- Use heading levels from original heading results for heading faces.
- Keep normal completion text height for heading faces.
- Keep row, result, row-context, and configuration metadata on candidates.
- Preserve Rust row order in standard ~completing-read~.
- Resolve duplicate candidates to the correct original result.

** Non-goals

- Do not implement the public interactive query command.
- Do not execute result actions.
- Do not add Consult.
- Do not sort, truncate, pad, or expand presentation rows in Emacs.
- Do not implement watcher or cached-view lifecycle code.

** Architecture

Keep candidate construction and face mapping in ~org-files-db-presentation.el~.

Store the effective configuration name on the decoded presentation object after a one-shot query.

Build one searchable candidate string per Rust row. Use a separate propertized display string for the Rust-prepared visible row.

Append a hidden candidate identity. This identity keeps duplicate rows distinct after completion removes text properties.

Use a completion table that keeps Rust row order. Use standard ~completing-read~ for selection.

** Risks & assumptions

Rust ~display_text~ already contains truncation and padding for each cell.

Emacs only joins prepared cells into one visible row. It does not change their content.

Completion frontends can remove text properties from the selected string. The hidden identity therefore remains part of the candidate string.

* Results

** Approach

~org-files-db-presentation.el~ now builds one lightweight completion candidate for each prepared Rust row.

The candidate keeps complete cell ~search_text~ in its underlying string. A separate display property shows the Rust-prepared cell text.

Semantic roles map to package faces. Heading roles use ~level~ or ~heading_level~ from the original result.

Heading faces inherit Org heading faces and set ~:height 1.0~. This keeps normal completion text height.

Each candidate keeps its row, original result, row context, and effective configuration name as text properties.

A hidden private-use identity keeps duplicate candidate strings distinct. Selection can resolve the correct result after text properties disappear.

The completion table uses identity sort functions. This keeps the row order that Rust produced.

~org-files-db-query-results~ stores the effective configuration name on the decoded presentation object.
