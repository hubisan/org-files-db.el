Implement Step 3 of the ~org-files-db.el~ rebuild.

* Planning

** Problem summary

The rebuilt package can call ~orgfdb~, but it cannot use the Rust presentation interface yet.

Step 3 needs one serializer for ~PresentationSpec~ and one decoder for ~presentation-json~ version 2.

** Goals

- Serialize flat Emacs column, sort, and row-source configuration to ~PresentationSpec~ JSON.
- Keep Rust responsible for presentation semantics and presentation validation.
- Decode ~presentation-json~ version 2 into small Emacs data structures.
- Keep original results separate from presentation rows.
- Resolve row results through ~result_index~.
- Decode roles through ~schemas.role_values~.
- Preserve ~row_context~ metadata.
- Treat a null ~display_text~ as ~search_text~.
- Add ~org-files-db-query-results~ as a data-only query interface.

** Non-goals

- Do not build completion candidates.
- Do not add faces.
- Do not run actions.
- Do not add watcher or cached-view commands.
- Do not duplicate Rust column support, include inference, sorting, row expansion, width, truncation, padding, or outline construction.

** Architecture

Keep ~PresentationSpec~ serialization and version 2 decoding in ~org-files-db-presentation.el~.

Keep query expression handling and the one-shot presentation call in ~org-files-db-query.el~.

Represent decoded rows and cells with small Emacs structures. Keep the original ~results~ vector once on the presentation response.

Rows store only ~result_index~, ~row_context~, and cells. A helper resolves the original result when a caller needs it.

Use the wire schemas for positional field indexes and semantic role decoding.

* Results

** Approach

~org-files-db-presentation.el~ now owns ~PresentationSpec~ serialization and version 2 decoding.

The serializer maps flat Emacs forms to the Rust JSON shape. It does not keep a local registry of supported columns.

The decoder compiles wire schema positions once per response. Rows and cells use these compiled positions.

Original results stay in one response vector. Each row stores only its ~result_index~, ~row_context~, and decoded cells.

~org-files-db-query-results~ runs one synchronous ~presentation-json~ query and returns the decoded presentation response.
