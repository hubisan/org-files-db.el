[[./archive/2026-08-08--searchable-visual-truncation.org][Task details]]

Goal:

- Make column truncation purely visual.
- Keep the complete untruncated candidate text available to standard Emacs completion and Consult filtering.
- Represent truncation through text properties instead of removing searchable text from the candidate.
- Preserve identical behaviour for fresh candidates and later cached candidates.

** Candidate representation

A completion candidate must retain its complete logical text.

Truncation changes only its visual representation.

Use the ~display~ text property for truncated column regions instead of replacing the underlying text with the truncated value.

Conceptually:

#+begin_example
underlying candidate:
TODO  Implement generation-aware asynchronous pre-caching for predefined views  project.org

displayed candidate:
TODO  Implement generation-awar…views  project.org
#+end_example

The underlying candidate must still contain:

#+begin_example
asynchronous
pre-caching
predefined
#+end_example

even though these parts may not be visible.

Do not append artificial hidden search strings to candidates.

Do not maintain separate "search candidate" and "display candidate" strings when one propertized candidate can represent both.

** Truncation

Apply truncation only through presentation properties.

A column with:

#+begin_example
:width auto
:width (max N)
:width (fixed N)
#+end_example

may shorten its displayed representation when required, but the underlying substring belonging to that column remains complete.

Support the existing truncation positions:

- left
- middle
- right

The truncation marker is part of the displayed replacement text only.

For example:

#+begin_src emacs-lisp
(file-name
 :width (max 30)
 :truncate (:position middle :marker "…"))
#+end_src

may display:

#+begin_example
very-long-proje…notes.org
#+end_example

while the candidate still contains the complete original file name.

** Completion semantics

Standard ~completing-read~ must filter against the complete underlying candidate string.

Consult must likewise be able to match text that exists only in a visually truncated-away region.

For example, given:

#+begin_example
Implement generation-aware asynchronous pre-caching for predefined views
#+end_example

displayed as:

#+begin_example
Implement generation-awar…views
#+end_example

filtering for:

#+begin_example
asynchronous
#+end_example

must still match that candidate.

The same applies to:

#+begin_example
pre-caching
predefined
#+end_example

Do not introduce a custom completion implementation merely to support this behaviour.

Use normal completion candidate semantics.

** Column formatting

Keep logical value extraction separate from visual formatting.

Conceptually:

#+begin_example
complete column value
→ determine displayed width
→ create truncated display string when required
→ attach display property to complete candidate region
#+end_example

Do not truncate the logical column value before constructing the candidate.

Do not make width calculation depend on the already truncated display string.

Shared width calculation continues to use the complete logical values.

** Candidate metadata

Preserve all existing candidate metadata and identity behaviour.

This includes:

- original ~org-files-db-result~ metadata
- duplicate candidate identity
- Consult metadata
- Embark actions
- completion categories
- visible faces and formatting

Adding ~display~ properties for truncation must not replace or destroy existing text properties.

Where several properties apply to the same candidate region, compose them correctly.

** Cached candidates

The future predefined-view cache must store the same propertized candidates that fresh presentation produces.

A cached candidate therefore conceptually contains:

#+begin_example
complete underlying candidate text
display properties containing truncated presentation
result/action metadata
other presentation properties
#+end_example

Do not store separate full and truncated candidate strings merely for truncation.

When candidates are serialized through a cache dump, serialization must preserve:

- complete underlying text
- ~display~ properties
- result metadata
- other required text properties

After reading the dump, the candidate must remain immediately usable by ~completing-read~ without reconstructing searchable text or rerunning formatting.

A warm cache lookup must not:

- rerun value extraction
- recalculate truncation
- reconstruct complete values
- reapply display properties
- reformat candidates

The cached candidate should already be ready for completion.

** Dump compatibility

Add a regression test showing that a propertized candidate survives a ~prin1~ / ~read~ round trip.

Verify after the round trip that:

- the underlying string is still complete
- the ~display~ property is still present
- result metadata is still present
- hidden text remains searchable

Use ~read-eval~ disabled when reading test dumps.

This test prepares the candidate representation for the later async cache rewrite without implementing that cache here.

** Standard completing-read test

Add an isolated regression using several candidates where only one candidate contains the matching text in a truncated-away region.

Example candidates:

#+end_example

Display the second candidate as:

#+begin_example

#+end_example

Using a completion style capable of substring matching, filtering for:

#+begin_example
asynchronous
#+end_example

must leave only the second candidate.

Verify that the selected underlying value is still:

#+begin_example
Implement generation-aware asynchronous pre-caching for predefined views
#+end_example

** Consult test

Add the equivalent regression for the Consult completion path.

With several candidates present, filtering for text that exists only in the truncated-away part must select the correct candidate.

Do not rely only on visual inspection.

Assert the selected logical candidate value.

** Truncation tests

Cover at least:

- suffix/right truncation
- prefix/left truncation
- middle truncation
- fixed-width columns
- maximum-width columns
- non-truncated values
- non-ASCII text
- custom truncation markers
- empty truncation marker

For every truncation mode verify both:

1. the visible representation is correct
2. the complete underlying value remains searchable

** Metadata tests

Verify that adding visual truncation does not break:

- result lookup
- duplicate candidate identity
- default result action
- Embark actions
- Consult metadata
- faces and other existing display properties

Where a candidate contains several columns, truncating one column must not affect the logical text or properties of neighbouring columns.

** Performance

Do not introduce a second complete candidate copy solely for searchability.

The normal candidate should contain the complete text already.

The truncated representation exists only as the ~display~ property value for the affected region.

Avoid rerunning column extraction when constructing display properties.

Add or extend the presentation benchmark so that truncation with ~display~ properties can be compared with the existing candidate preparation path for approximately:

- 1,000 candidates
- 10,000 candidates

The implementation should remain suitable for producing fully prepared candidates in an async worker later.

** Documentation

Document that:

- truncation affects only what is displayed
- completion continues to search the complete value
- this works with normal Emacs completion
- users do not need a separate search configuration for truncated columns

Avoid documenting internal cache or serialization details in the user-facing README unless they are relevant to observable behaviour.

** Acceptance criteria

- Truncation never removes text from the logical completion candidate.
- The complete candidate text is used for completion filtering.
- Truncated presentation is implemented with ~display~ text properties or an equivalent presentation-only mechanism.
- Standard ~completing-read~ can match text that is only present in a truncated-away region.
- Consult can match text that is only present in a truncated-away region.
- Multiple-candidate tests prove that only the logically matching candidate remains.
- Left, middle, and right truncation preserve complete searchable values.
- Fixed and maximum width columns preserve complete searchable values.
- Candidate metadata and actions remain unchanged.
- A ~prin1~ / ~read~ round trip preserves the full candidate, its visual truncation, and required metadata.
- Future cached candidates can be used directly without reconstructing searchable text.
- No separate full/search candidate copy is required solely to support truncation.
- Existing tests continue to pass.
- ~make ci~ passes.
