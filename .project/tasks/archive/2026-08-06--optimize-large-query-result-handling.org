Goal: Make synchronous queries returning 10,000 or more results fast enough that the completion interface appears promptly and filtering remains effectively instant.

Keep the existing synchronous public interface.

Do not add asynchronous query commands, Emacs Lisp worker threads, streaming, pagination, or lazy result loading as part of this task.

Follow the same general performance model used successfully by Vulpea:

#+begin_example
database or CLI results
→ build each display candidate once
→ associate it directly with the original result
→ pass the prepared candidates to completion
#+end_example

The optimized ~org-files-db~ pipeline additionally needs shared-width handling:

#+begin_example
orgfdb response
→ parse once
→ normalize column specifications once
→ calculate each required result value once
→ calculate each displayed cell once
→ calculate shared widths from cached cells
→ format each candidate once
→ open completion
#+end_example

Once completion opens, filtering and redisplay must reuse the already prepared candidate strings without invoking result extraction, column formatting, width calculation, or face processing again.

Do not introduce a separate asynchronous command or require users to choose between synchronous and asynchronous execution.

*** Build cached presentation rows

Represent every visible row explicitly.

Conceptually:

#+begin_src emacs-lisp

  result
  source
  original-position
  row-source
  row-value
  cells
  sort-keys
  candidate)
#+end_src

A normal result creates one presentation row.

Tag, property, and keyword expansion may create several rows sharing the same presentation source and original result.

Each cached cell contains at least:

#+begin_example

#+end_example

The preparation pipeline becomes:

#+begin_example

→ presentation sources
→ row expansion

→ cached sort keys
→ stable sorting
→ shared-width calculation
→ candidate formatting
#+end_example

Calculate each displayed value at most once per presentation row.

Do not call the general column extractor again during width calculation or candidate formatting.

*** Calculate widths from cached cells

Calculate final shared widths from cached display widths.

For ~(fixed N)~:

- use ~N~ directly
- do not scan cell widths to determine the column width
- still calculate each cell once because its value is needed for display and filtering

For ~(max N)~:

- track the largest cached display width
- stop updating the width accumulator once it reaches ~N~
- continue preparing remaining cells because they are still required as candidates

For ~auto~:

- inspect all cached display widths
- preserve exact existing behaviour
- do not estimate or sample

Avoid creating a temporary list of all widths before reducing it.

Do not use a pattern such as:

#+begin_src emacs-lisp
(apply #'max
       (mapcar #'string-width values))
#+end_src

Update width accumulators directly while rows are prepared or through one allocation-free pass over cached cells.

Filtering must operate on already prepared candidate strings.

All configured visible values must remain searchable.

The internal uniqueness component must not be visible and must not meaningfully affect filtering.

- sanitize it once

* Planning

** Problem summary

Large synchronous query and search result sets repeatedly extracted column values, recalculated widths, sanitized faces, and formatted candidates. Candidate selection also needed a fallback scan when completion returned a string without text properties.

** Goals

- Prepare each displayed cell once per result row.
- Normalize column definitions and inferred CLI includes once per invocation.
- Reuse cached strings and display widths for shared-width calculation and candidate formatting.
- Sanitize each distinct face once per presentation.
- Preserve original results, duplicate visible candidates, configured order, Embark metadata, and live-search behaviour.
- Keep complete truncated values searchable without rebuilding candidates during filtering.
- Add repeatable synthetic and representative benchmarks.

** Non-goals

- Asynchronous commands, worker threads, streaming, pagination, or lazy result loading.
- Generation-aware predefined-view caching.
- Adding sorting or row-expansion behaviour that is not yet implemented by the package.
- Switching the production JSON representation without benchmark evidence.

** Architecture

Compile configured columns into normalized presentation specifications. Build one lightweight source and row per result, cache each logical and displayed cell value, derive shared widths from the cached display widths, cache sanitized faces locally, and format each candidate once. Attach the original result and row metadata directly to each candidate and keep a direct lookup for completion strings whose properties were removed.

** Execution plan

1. Introduce normalized presentation columns, sources, cells, rows, and complete presentations in Core.
2. Route query, one-shot search, and live search through the shared eager presentation pipeline.
3. Preserve full truncated values as hidden searchable candidate text and add compact invisible identities for duplicates.
4. Add direct candidate-to-result lookup and preserve completion order.
5. Add presentation and JSON-representation benchmark helpers with deterministic fixtures.
6. Add regression tests for caching, width handling, face caching, duplicate identity, direct lookup, searchable truncation, Unicode, and hash-table access.
7. Update README and changelog.

** Risks & assumptions

- The package currently has no implemented presentation sorting or row expansion, so the new structures retain fields for those future stages without adding a second speculative implementation.
- Theme-sensitive face properties must remain presentation-local.
- Standard completion and Consult must receive the same already prepared candidate strings.

* Results

** Approach

Replaced the repeated width-and-format loops with one eager presentation pipeline. Column options and required includes are compiled once. Result-level values are cached lazily, every visible cell records its logical value, display string, display width, and source face, and shared widths consume those cached widths. Distinct faces are sanitized once per invocation. Candidates are formatted once, retain hidden full values only where truncation occurred, carry compact invisible identities, and expose direct result and row metadata.

Query, one-shot search, and live search now pass normalized columns into the same Core implementation. Production JSON remains alist-based, while the benchmark can compare alists and hash tables through the shared access functions.
