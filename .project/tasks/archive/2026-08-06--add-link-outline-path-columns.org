Goal: Display the outline hierarchy containing a link and the outline hierarchy of its resolved target as separate configurable columns.

*** Column names

For link results, provide two explicit columns:

- ~source-outline-path~ shows the hierarchy in which the link occurs.
- ~target-outline-path~ shows the hierarchy of the resolved link target.

Use ~outline-path~ for heading and search results.

Do not use the ambiguous ~outline-path~ name as the documented link column.

Existing support for ~outline-path~ on link results may remain temporarily as an alias for ~source-outline-path~, but new documentation and examples must use the explicit column names.

*** Source outline path

~source-outline-path~ represents the Org hierarchy containing the matched link.

Example source:

#+begin_src org
,* Applications
,** Editors
,*** Emacs
,**** [[file:packages.org][Packages]]
#+end_src

The source outline path is:

#+begin_example
Applications » Editors » Emacs
#+end_example

The link itself is not an outline component.

The column uses structured source context returned for link results.

The query command must request the required source data automatically when ~source-outline-path~ is configured.

Prefer the structured source heading outline path when available.

A ~node_path~ returned through the ~path~ include may be used when it represents the same source hierarchy.

Do not require ~--output outline~ merely to calculate this column.

*** Target outline path

~target-outline-path~ represents the hierarchy of the resolved target.

Example target:

#+begin_src org
,* heading 1
,** heading 2
,*** heading 3
:PROPERTIES:
:CUSTOM_ID: 4cd16e0c-cd97-42c7-8338-b4208e02224c
:END:
#+end_src

Given a resolved link to ~heading 3~, the target data contains:

#+begin_src json
"target": {
  "file": {
    "title": "test-subheading"
  },
  "heading": {
    "title": "heading 3",
    "outline_path": [
      "heading 1",
      "heading 2",
      "heading 3"
    ]
  }
}
#+end_src

The displayed target outline path is:

#+begin_example
heading 1 » heading 2 » heading 3
#+end_example

The query command must automatically request ~--include target~ when ~target-outline-path~ is configured.

No additional query may be executed for each target.

*** File targets

When the resolved target is a file rather than a heading:

- With ~:include-root t~, display the target file title.
- With ~:include-root nil~, display an empty value.

When the target is a heading, the target file title is included only when ~:include-root t~.

Example:

#+begin_example
test-subheading » heading 1 » heading 2 » heading 3
#+end_example

*** Unresolved targets

~target-outline-path~ is empty when the link target is:

- unresolved
- ambiguous
- external
- unsupported
- missing structured target data

Do not display the authored raw target as an outline path.

Other columns such as ~link-target~ and ~resolution-status~ continue to expose those details.

*** Shared outline options

Both columns support the same outline options:

#+begin_src emacs-lisp
(source-outline-path
 :separator " » "
 :include-root nil
 :include-match t
 :width (max 50)
 :truncate (:position right :marker "…"))

(target-outline-path
 :separator " » "
 :include-root nil
 :include-match t
 :width (max 50)
 :truncate (:position middle :marker "…"))
#+end_src

The options have the following meaning:

- ~:separator~ separates path components.
- ~:include-root~ includes the source or target file root.
- ~:include-match~ includes the final heading component.
- ~:width~ controls the shared column width.
- ~:truncate~ controls shortening when the final width is exceeded.

The global outline defaults also apply:

#+begin_src emacs-lisp
org-files-db-outline-path-separator
org-files-db-outline-path-include-root
org-files-db-outline-path-include-match
#+end_src

*** Include inference

Determine required CLI includes from the configured columns.

At minimum:

#+begin_example
source-outline-path  → source or path
target-outline-path  → target
#+end_example

When both columns are configured, invoke the CLI with all required includes in one call.

Conceptually:

#+begin_src sh
orgfdb query \
  --include source,target \
  '(links (status "resolved"))'
#+end_src

If ~path~ is required for source hierarchy instead of ~source~, combine it in the same invocation:

#+begin_src sh
orgfdb query \
  --include path,target \
  '(links (status "resolved"))'
#+end_src

Do not require users to specify includes manually merely because they selected these columns.

Do not request expensive includes that are not needed by the configured columns or actions.

*** Output mode

Keep the normal link query output flat for completion and column formatting.

~--output outline~ changes the shape of the result output and is intended for hierarchical output, not for providing individual column values.

The package's Org exporter may still construct outline output from the included path information.

Do not maintain separate flat and outline query execution paths solely for these columns.

*** Default link columns

Update the configurable link-column defaults to use explicit source and target names where appropriate.

Example:

#+begin_src emacs-lisp
(setq org-files-db-link-columns
      '((source-outline-path
         :width (max 50))
        (link-description
         :width (max 40))
        (target-outline-path
         :width (max 50))
        (resolution-status
         :width (fixed 10))
        (file-name
         :width (max 30))))
#+end_src

The target column need not be part of the built-in default if requesting target information for every link would be undesirable.

It must nevertheless be available as a documented supported column.

*** README documentation

Document:

- ~source-outline-path~ as the hierarchy containing the link
- ~target-outline-path~ as the hierarchy of the resolved target
- unresolved targets producing an empty target path
- both columns supporting the standard outline and truncation options
- required includes being selected automatically by the package

Do not imply that ~--output outline~ is required.

*** Acceptance criteria

- Link results support ~source-outline-path~.
- Link results support ~target-outline-path~.
- The source path describes where the link occurs.
- The target path describes the resolved target hierarchy.
- File roots can be included independently through ~:include-root~.
- The final heading can be omitted through ~:include-match nil~.
- Unresolved and external targets produce an empty target path.
- Configured columns automatically add the required CLI includes.
- Source and target data are retrieved in one CLI invocation.
- No per-result target queries are executed.
- Flat query output remains usable for completion.
- The columns support separators, widths, and general truncation options.
- Tests cover nested source headings, nested target headings, file targets, root inclusion, match exclusion, unresolved targets, custom separators, include inference, and simultaneous source and target columns.

** Problem summary

Link results currently expose ~source-outline-path~ only as an alias of the generic path formatter, always request ~path~, and do not support resolved target hierarchies or per-column outline options.

** Goals

- Format source and resolved target outline paths independently.
- Infer ~path~ and ~target~ includes from configured query columns.
- Preserve flat query output and a single CLI invocation.
- Add shared outline defaults and general column truncation options.
- Cover link path semantics and include inference with Buttercup tests.

- Change the orgfdb JSON contract or database schema.
- Execute per-result target queries.
- Add a separate link-query execution path.

- Read source context from structured source data, falling back to ~node_path~ from the ~path~ include.
