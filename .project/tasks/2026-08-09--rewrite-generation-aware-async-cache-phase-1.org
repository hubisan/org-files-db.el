* Planning

** Problem summary

The existing predefined-view cache mixed polling, persisted/cache-limit concerns, and Phase 2-style generation delta patching into the main lifecycle.  Phase 1 needs a smaller architecture whose correctness and latency can be measured before incremental refresh is attempted.

** Goals

- Replace the existing cache with asynchronous complete view rebuilds.
- Build complete ready-to-use completion candidates in one child Emacs per rebuild and transport the large result through a temporary readable-Lisp dump.
- Keep published warm entries entirely in parent Emacs memory and make warm lookup avoid CLI, parsing, presentation rebuilding, and cache-file access.
- Use file notifications as the only database-change wake-up and Rust ~status~ as the authority for database identity and committed generation.
- Cancel and supersede obsolete generation work safely.
- Add lifecycle tracing and benchmarks for worker work, dump transport, parent blocking, raw file events, generation detection, waiting, and cancellation.
- Keep every user-facing ~defcustom~ in ~org-files-db-core.el~.

** Non-goals

- Do not use ~orgfdb changes~.
- Do not use ~--restrict-files-json~ from the cache.
- Do not implement incremental result/candidate patching, width maintenance, or delta dumps.
- Do not add polling or a polling fallback.

** Architecture

Use one global cache mode with one FIFO queue and at most one active ~async.el~ child.  Enabling resolves authoritative status once per effective configuration, installs a directory file-notify watcher for the canonical SQLite path, and queues every ~:pre-cache t~ view.  Each worker performs query/search execution, JSON normalization, presentation preparation, sorting, width calculation, candidate formatting, and metadata construction, then writes one complete transport dump.  The parent callback rechecks authoritative status, safely reads and validates the dump, atomically replaces the published in-memory entry, deletes the dump, and records blocking/GC metrics.  Relevant raw file events are coalesced only by a short one-shot debounce timer before a status check.  A newer required database identity/generation cancels older running or queued jobs before replacement work is started.

** Execution plan

- Implement the Phase 1 worker, queue, dump transport, publication, waiting, file-notify, generation, cancellation, and cleanup lifecycle.
- Reuse the existing presentation pipeline inside the child so query/search semantics, metadata, actions, sorting, and truncation stay aligned with fresh execution.
- Add structured benchmark records and concise interactive reports.
- Replace Phase 2-oriented cache tests and synthetic benchmark code with Phase 1 coverage.
- Update README and CHANGELOG.

** Risks & assumptions

- ~async.el~ 1.9.9 starts a fresh ~-Q~ child and resolves its own library path when each child is started, so the cache must explicitly reuse the path found when cache mode is enabled.
- Parent publication necessarily remains synchronous while reading and validating the completed dump; this cost must be measured rather than hidden.
- File notifications are wake-up signals only and can be noisy; correctness comes from the subsequent Rust status result, not from SQLite filename activity itself.

* Results

** Approach

Replaced the former cache with a Phase 1-only in-memory lifecycle.  One queued rebuild maps to one short-lived child Emacs and one short-lived dump.  The child owns all expensive candidate preparation; the parent owns authoritative final validation and atomic publication.  File notifications only schedule a one-shot status check, and generation transitions replace stale work instead of patching it.
