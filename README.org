Emacs interface for [[https://github.com/hubisan/org-files-db][org-files-db]].  The package keeps indexing and SQLite access in the ~orgfdb~ executable and uses its JSON interfaces for queries and search.

* Requirements

- Emacs 29.4 or newer
- ~orgfdb~ installed or available through an explicit path
- [[https://github.com/jwiegley/emacs-async][async.el]] for background predefined-view cache refreshes
- [[https://github.com/minad/consult][Consult]] for live FTS5 search
- [[https://github.com/oantolin/embark][Embark]] for exporting the currently filtered completion candidates
- [[https://emacs-eask.github.io/][Eask]] for development

Consult and Embark are optional at runtime.  Ordinary queries, one-shot search, views, actions, and dynamic blocks work without them.  Pre-caching is disabled unless a predefined view opts in with ~:pre-cache t~.

* Configuration

#+begin_src emacs-lisp
(setq org-files-db-executable "orgfdb")
(setq org-files-db-config-file "~/org/org-files-db.toml")
#+end_src

Run ~M-x org-files-db-check-setup~ to inspect the resolved executable, configuration file, version, and read-only database access.

The global file is the default for every operation.  Query, search, live-search, action, setup-diagnostic, view, and dynamic-block entry points may override it for one invocation.  Omitting ~:config-file~ inherits the global value, a path selects another configuration, and an explicit ~nil~ invokes ~orgfdb~ without ~--config~.

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 nil
 nil
 :config-file "~/org/private/org-files-db.toml")

(org-files-db-query
 '(headings (tags "public"))
 nil
 nil
 :config-file nil)
#+end_src

Configuration paths are expanded and must identify readable files.  Relative paths are resolved against ~default-directory~ at invocation time.

* Query

~org-files-db-query~ accepts an ~orgfdb~ query expression as Emacs Lisp data:

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 '((todo-keyword :width (fixed 8))
   (priority :width auto)
   (outline-path :width (max 80))
   (file-name :width (max 30))))
#+end_src

The result list uses standard Emacs completion and therefore works with the default UI, Vertico, Icomplete, and Fido.  The selected result is opened at its stored UTF-8 byte location by default.

Supported column widths are:

- ~auto~: use the widest value in the current result set
- ~(max N)~: calculate automatically, capped at ~N~ columns
- ~(fixed N)~: always use ~N~ columns

Default columns can be customized separately for headings, files, links, and search results.

** Outline paths and truncation

Heading and search results use the ~outline-path~ column.  Link results use two explicit columns: ~source-outline-path~ is the hierarchy containing the link, while ~target-outline-path~ is the hierarchy of its resolved target.  Unresolved, ambiguous, external, unsupported, and structurally incomplete targets produce an empty target path rather than displaying the authored link target.

#+begin_src emacs-lisp
(setq org-files-db-outline-path-separator " » ")
(setq org-files-db-outline-path-include-root nil)
(setq org-files-db-outline-path-include-match t)

(org-files-db-query
 '(links (status "resolved"))
 '((source-outline-path
    :separator " » "
    :include-root nil
    :include-match t
    :width (max 50)
    :truncate (:position right :marker "…"))
   (link-description :width (max 40))
   (target-outline-path
    :separator " » "
    :include-root t
    :include-match t
    :width (max 50)
    :truncate (:position middle :marker "…"))
   (resolution-status :width (fixed 10))))
#+end_src

~:separator~ controls the text between components.  ~:include-root~ includes the corresponding source or target file title.  ~:include-match nil~ omits the final source heading or resolved target heading.  For a target that resolves directly to a file, ~target-outline-path~ is empty unless ~:include-root t~ is used.

The package infers required CLI includes from the configured columns.  ~source-outline-path~ requests source path context and ~target-outline-path~ requests structured target context; both are retrieved in the same flat query invocation.  Users do not need to add ~--include~ or switch to outline output.  For compatibility, ~outline-path~ on link results currently behaves like ~source-outline-path~, but new configurations should use the explicit link column name.

Truncation is available for every displayed column.  Customize the defaults with ~org-files-db-truncate-position~ and ~org-files-db-truncate-marker~, or override them per column with ~:truncate (:position left|middle|right :marker STRING)~.  The marker counts toward the final column width, and an empty marker performs hard truncation.  Truncation is visual only: standard Emacs completion and Consult continue to search the complete untruncated column value, including text that is not currently visible.

** Result sorting

Query and search results can be sorted by one or more public columns before completion, export, or dynamic-block rendering.  A sort column does not need to be displayed:

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 '((todo-keyword)
   (outline-path :width (max 80))
   (file-name :width (max 30)))
 nil
 :sort
 '((priority :direction asc :missing last)
   (deadline-raw :direction asc :missing last)
   (outline-path :direction asc)))
#+end_src

Each sort key accepts ~:direction asc|desc~, ~:missing first|last~, and ~:case-fold t|nil~.  Defaults are ascending order, missing values last, and case-insensitive text comparison.  Equal rows retain their original ~orgfdb~ order.

Text is compared using complete untruncated values.  ~line-number~ and search ~rank~ are numeric, Org priorities use their natural ~A~, ~B~, ~C~ order, planning timestamps are chronological, outline paths are compared by path components rather than their display separator, and ~tags~ compares the complete tag collection.

Default sorting can be configured separately:

#+begin_src emacs-lisp
(setq org-files-db-heading-sort nil)
(setq org-files-db-file-sort nil)
(setq org-files-db-link-sort nil)
(setq org-files-db-search-sort nil)
#+end_src

Nil defaults preserve the order returned by ~orgfdb~.  This is especially important for search, where the normal order represents relevance.  Omitting ~:sort~ inherits the corresponding default; an explicit ~:sort nil~ preserves the CLI order for that invocation even when a default is configured.

Supported heading sort columns include ~title~, ~todo-keyword~, ~todo-type~, ~priority~, ~outline-path~, ~tags~, ~file-title~, ~file-name~, ~file-path~, ~line-number~, ~scheduled-raw~, ~deadline-raw~, and ~closed-raw~.  File results support ~file-title~, ~file-name~, ~file-path~, ~tags~, and ~line-number~.  Link results support ~link-type~, ~link-target~, ~link-description~, ~resolution-status~, ~source-outline-path~, ~target-outline-path~, ~file-name~, ~file-path~, and ~line-number~.  Search supports ~title~, ~outline-path~, ~file-name~, ~file-path~, ~line-number~, and ~rank~.

** Large result sets

Query and search presentation is eager and synchronous.  The package normalizes column definitions once, extracts each displayed value once per row, calculates shared widths from cached cell widths, sanitizes each distinct face once, and formats every completion candidate once.  Completion filtering and redisplay operate only on the prepared candidate strings; selected actions and Embark still receive the original result object.

Duplicate visible candidates retain separate invisible identities and direct result metadata.  Prepared CLI order is preserved, selection does not scan the complete candidate list, and visually shortened values remain complete in the underlying completion candidate.  Truncated column regions use presentation-only ~display~ properties instead of appended hidden search copies.

For a real invocation, profile Emacs with ~M-x profiler-start~, run the query, and inspect ~M-x profiler-report~.  The development benchmark covers synthetic sets of 100, 1,000, 10,000, and 50,000 rows, representative inexpensive and expensive columns, visual-only truncation at 1,000 and 10,000 rows, and alist versus hash-table JSON parsing:

#+begin_src shell
emacs -Q -L lisp -l benchmarks/org-files-db-benchmark.el \
  --eval '(org-files-db-benchmark-run 3)'
#+end_src

Run ~M-x org-files-db-benchmark-query~ to separate real CLI execution, JSON parsing, result normalization, presentation, and total time for the current database.  Run ~M-x org-files-db-benchmark-compare-frontends~ interactively to compare initialization of standard completion and Consult using the same already prepared candidates.  Consult remains optional and normal query completion does not depend on it.

Run ~M-x org-files-db-benchmark-view-cache~ to compare synthetic full candidate preparation, readable-Lisp dump write/read, direct in-memory warm lookup, and warm completion.  For a real cache lifecycle, use ~M-x org-files-db-cache-benchmark-report~ after an initial or file-notify-triggered rebuild; ~M-x org-files-db-cache-file-notify-trace~ shows every raw filesystem event.

Run ~M-x org-files-db-benchmark-sorting~ to benchmark 1,000 and 10,000 prepared rows with multiple text keys, numeric keys, timestamp keys, and complete tag collections.  The report measures sort-key preparation and sorting separately from value extraction, width calculation, face preparation, and candidate formatting.

* Search

Perform one FTS5 search:

#+begin_src emacs-lisp
(org-files-db-search
 "title:sqlite AND body:index*"
 nil
 nil
 :scope 'all
 :sort nil
 :config-file "~/work/org-files-db.toml")
#+end_src

Start Consult-powered live search with ~M-x org-files-db-search-live~.  Search starts after ~org-files-db-search-min-input~ characters, debounces changing input, and discards obsolete processes.

#+begin_src emacs-lisp
(org-files-db-search-live
 nil
 nil
 :scope 'title
 :config-file "~/work/org-files-db.toml")
#+end_src

The former leading positional search scope remains accepted for compatibility, including before ~:config-file~, but keyword arguments are preferred.

Search accepts the same ~:sort~ syntax as queries.  With no configured search sort, results remain in ~orgfdb~ relevance order.  For example, ~:sort '((title :direction asc))~ alphabetizes one invocation, while ~:sort nil~ explicitly keeps relevance order.

* Predefined views

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("open-tasks"
         :command query
         :config-file "~/org/private/org-files-db.toml"
         :query (headings (not (done)))
         :sort ((priority :direction asc :missing last)
                (outline-path :direction asc))
         :columns ((todo-keyword :width (fixed 8))
                   (outline-path :width (max 80))))
        ("project-search"
         :command search
         :expression "org-files-db"
         :scope title)
        ("resolved-links"
         :command query
         :query (links (status "resolved"))
         :columns ((source-outline-path :width (max 50))
                   (link-description :width (max 30))
                   (target-outline-path :width (max 50))))
        ("public-tasks"
         :command query
         :config-file nil
         :query (headings (tags "public")))))
#+end_src

Use ~M-x org-files-db-views-query~ or ~M-x org-files-db-views-search~.  From Lisp, pass the view name directly.

A view without ~:config-file~ inherits ~org-files-db-config-file~.  A path selects that configuration for the delegated query or search, while an explicit ~nil~ disables ~--config~ for the view.

A view without ~:sort~ inherits the configured default for its result type.  A view-specific sort overrides that default, while an explicit ~:sort nil~ preserves ~orgfdb~ order.

** Generation-aware pre-caching

Pre-caching is an advanced opt-in feature for predefined views.  Add ~:pre-cache t~ to mark a view as eligible, then enable the global cache mode:

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("all-headings"
         :command query
         :pre-cache t
         :query (headings)
         :columns
         ((todo-keyword :width (max 10))
          (title :width (max 70))
          (file-name :width (max 30))))
        ("project-search"
         :command search
         :pre-cache t
         :expression "org-files-db"
         :scope title
         :columns
         ((title :width (max 70))
          (file-name :width (max 30))))))
#+end_src

#+begin_src emacs-lisp
(org-files-db-cache-mode 1)
#+end_src

Enabling ~org-files-db-cache-mode~ resolves ~database_path~, ~database_id~, and committed ~generation~ through ~orgfdb status~, installs the required file notification watcher, and queues every configured ~:pre-cache t~ view.  Rebuilds are asynchronous and use one child Emacs at a time.  The child performs the query or search, JSON parsing and normalization, sorting, shared-width calculation, visual formatting and truncation, searchable candidate construction, and candidate metadata preparation.

Each worker writes the complete ready-to-publish cache entry to a unique temporary readable-Lisp dump.  Only small job metadata and timings return through ~async.el~.  The parent reads the dump once, validates the job, database identity, and generation, atomically replaces the in-memory entry, and deletes the dump.  The dump is transport only: a warm view never reads it again.  Normal warm use is therefore only an in-memory cache lookup followed by completion.  Direct calls to ~org-files-db-query~ and ~org-files-db-search~ always remain fresh and bypass the predefined-view cache.

SQLite ~file-notify~ events are the only database-change wake-up mechanism.  The watcher observes the canonical database location returned by Rust and the related SQLite database, ~-wal~, and ~-shm~ activity.  A short debounce coalesces filesystem bursts around actual notifications; there is no polling fallback and no periodic cache timer.  Filesystem activity only triggers a new ~orgfdb status~ check.  If ~database_id~ and committed ~generation~ are unchanged, the current cache is kept and no rebuild runs.

In Phase 1 every committed generation change causes a complete asynchronous rebuild of every affected pre-cached view.  The cache does not use ~orgfdb changes~, restricted-file queries, incremental candidate patching, or incremental width updates.  If a newer generation is detected while an older worker is still running, the older worker is terminated immediately, its transport dump is removed, and only the newest required generation is allowed to publish.  A callback whose job ID, database identity, or generation is obsolete performs cleanup only.

If a view is opened while its required generation is already rebuilding, Emacs waits for that existing asynchronous job while continuing to process child output.  If the job is superseded, the wait follows its replacement.  Initial pre-cache behaves the same way when no published entry exists yet.  Waiting is bounded by ~org-files-db-cache-wait-timeout~; failures never overwrite a previously valid published entry.

Cache management commands are:

- ~org-files-db-views-refresh-cache~
- ~org-files-db-views-refresh-all-caches~
- ~org-files-db-views-clear-cache~
- ~org-files-db-views-clear-all-caches~

Refresh commands start complete asynchronous rebuilds.  With a prefix argument they still use the asynchronous worker but wait until the replacement is published.  Clearing a cache does not modify the Rust database or the view definition.

All user-facing package options, including cache options, are defined in ~org-files-db-core.el~.  Cache lifecycle options are:

#+begin_src emacs-lisp
org-files-db-cache-file-notify-debounce
org-files-db-cache-wait-timeout
org-files-db-cache-debug
#+end_src

Set ~org-files-db-cache-debug~ non-nil for concise lifecycle diagnostics.  ~M-x org-files-db-cache-benchmark-report~ displays the newest structured cache lifecycle record.  Rebuild records include worker startup, query/search, JSON normalization, presentation phases, dump write/read/delete, final status validation, publication, main-Emacs blocking and GC measurements; warm lookups and interactive waits report their own latency.  For file-notify refreshes the lifecycle data also records the raw event count and event-to-generation/worker/dump/publication timing chain.  ~M-x org-files-db-cache-file-notify-trace~ lists every raw notification separately, so SQLite event bursts are not confused with logical generation rebuilds.

Disabling ~org-files-db-cache-mode~ terminates running work, clears queued rebuilds, removes all file notification watches and debounce timers, deletes owned transport dumps, and clears published cache entries.  After initial pre-cache completes and the database is unchanged, cache mode has no workers, no polling, no periodic timer, no CLI activity, and no candidate preparation.  Caches are in memory only and are rebuilt after Emacs restarts.

* Embark export

Query and search candidates use the ~org-files-db-result~ completion category.  With Embark installed, ~embark-export~ creates an Org buffer containing exactly the candidates matching the current minibuffer filter.

Customize:

- ~org-files-db-export-layout~ to ~flat~ or ~outline~
- ~org-files-db-export-linked-heading-style~ to ~preserve~ or ~resolve~

~preserve~ keeps authored links embedded in heading titles.  ~resolve~ follows those links and displays the effective target title.

* Result actions

The optional action argument of ~org-files-db-query~ and ~org-files-db-search~ receives the selected result object.  Package-owned execution metadata may be attached for follow-up operations.

Built-in actions and wrappers include:

- ~org-files-db-actions-open-result~
- ~org-files-db-actions-follow-heading-link~
- ~org-files-db-actions-insert-file-link~
- ~org-files-db-actions-insert-heading-link~
- ~org-files-db-actions-query-insert-file-link~
- ~org-files-db-actions-query-insert-heading-link~
- ~org-files-db-actions-rename-file-result~

File links support normal ~file:~, ~id:~, and file-plus-~CUSTOM_ID~ styles.  Heading links support ~id:~, file-plus-~CUSTOM_ID~, and title-based file search links.  Missing IDs are created with Org APIs and saved before the link is inserted.

~org-files-db-actions-rename-file~ updates resolved path-based links before renaming the target.  It preserves descriptions and heading or custom-ID search options, but the multi-file operation is not globally atomic.  Version control is strongly recommended.

Query and search results retain the effective configuration that produced them.  Follow-up CLI operations, such as indexed ID resolution or link discovery during rename, continue to use that configuration even if the global option changes later.

* Backlinks

~M-x org-files-db-actions-backlinks~ is a convenience wrapper around a normal link query for the current file or heading.  The returned objects are the source links, so selecting one jumps to the original link location.

* Org dynamic blocks

The package registers these block types:

#+begin_src org
,#+BEGIN: org-files-db-query :query "(headings (not (done)))" :layout flat
,#+END:

,#+BEGIN: org-files-db-query :query "(headings (not (done)))" :sort "((priority :direction asc) (outline-path :direction asc))" :layout flat
,#+END:

,#+BEGIN: org-files-db-query :view "open-tasks" :layout outline
,#+END:

,#+BEGIN: org-files-db-search :expression "sqlite AND index*" :scope all :layout flat
,#+END:

,#+BEGIN: org-files-db-query :query "(headings (tags \"private\"))" :config-file "~/org/private/org-files-db.toml" :layout flat
,#+END:

,#+BEGIN: org-files-db-search :expression "public report" :config-file none :layout flat
,#+END:

,#+BEGIN: org-files-db-backlinks :scope heading :layout flat
,#+END:
#+end_src

Update a block with ~org-update-dblock~ or all blocks with ~org-update-all-dblocks~.  Generated entries link back to their indexed source locations.

Direct blocks inherit the global configuration when ~:config-file~ is absent.  A path overrides it, and the dedicated value ~none~ disables ~--config~.  Blocks using ~:view~ inherit the selected view's configuration and must not also specify ~:config-file~.

Direct query and search blocks accept ~:sort~ as a safely read Lisp expression.  Blocks using ~:view~ inherit that view's sorting unless the block supplies its own ~:sort~.  An explicit ~:sort "nil"~ preserves the CLI order even when a global sort default is configured.

* API naming

Public names identify their owning module, while the two central operations stay concise:

#+begin_example
org-files-db-query             central query operation
org-files-db-search            central search operation
org-files-db-search-live       live search operation
org-files-db-actions-*         public result action
org-files-db-actions--*        private action helper
org-files-db-cache-*           cache module operation
org-files-db-cache--*          private cache helper
org-files-db-views-*           public view operation
org-files-db-views--*          private view helper
org-files-db-dblock-*          public dynamic-block insertion command
org-files-db-dblock--*         private dynamic-block helper
org-files-db-query--*          private query helper
org-files-db-search--*         private search helper
org-files-db-export-*          public export operation
org-files-db-export--*         private export helper

Names containing a double hyphen are internal implementation details and are not supported as public API.
