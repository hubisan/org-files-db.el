Emacs client for [[https://github.com/hubisan/org-files-db][org-files-db]]. The ~orgfdb~ command line tool indexes your Org files into a database and answers structural queries over them. This package lets you run those queries from Emacs, pick a result with standard completion, and act on it: open it, insert a link to it, follow its link, or rename its file.

* Requirements

- Emacs 29.3 or newer
- The ~orgfdb~ executable, installed or available through an explicit path
- Optional: [[https://github.com/oantolin/embark][Embark]] for result actions and exporting the filtered results

* Quick start

Tell Emacs where ~orgfdb~ and your configuration file are. A configuration has a name and points to an ~orgfdb~ configuration file. The default configuration is used whenever you do not select one.

#+begin_src emacs-lisp
(require 'org-files-db)

(setq org-files-db-configs '(("main" . "~/org/org-files-db.toml")))
(setq org-files-db-default-config "main")
#+end_src

Run ~M-x org-files-db-check-setup~ to verify the executable, the configuration file, the version and read access to the database.

Run a query with ~M-x org-files-db-query~ and enter a structural query at the prompt, for example:

#+begin_example
(headings (not (done)))
#+end_example

This lists all headings that are not done. Pick one with the usual completion interface (default UI, Vertico, Icomplete, Fido, ...) and press ~RET~ to open it. The same query from Lisp:

#+begin_src emacs-lisp
(org-files-db-query '(headings (not (done))))
#+end_src

* Configuration

~org-files-db-executable~ is the command name or path of ~orgfdb~ (default ~"orgfdb"~).

~org-files-db-configs~ is an alist of named configurations. Each entry is ~(NAME . FILE)~ with a unique non-empty name and the path of an ~orgfdb~ configuration file. Use several entries when you keep separate indexes, for example for work and private notes.

~org-files-db-default-config~ is the name of the entry that is used when none is selected. It is required as soon as ~org-files-db-configs~ is not empty.

#+begin_src emacs-lisp
(setq org-files-db-configs
      '(("main" . "~/org/org-files-db.toml")
        ("work" . "~/work/org-files-db.toml")))
(setq org-files-db-default-config "main")
#+end_src

Select a configuration for one call in one of these ways:

- Interactively, call ~org-files-db-query~ or ~org-files-db-check-setup~ with a prefix argument (~C-u~) to choose from ~org-files-db-configs~.
- From Lisp, pass ~:config "work"~ to ~org-files-db-query~.
- In a predefined view, set ~:config "work"~.

The configuration files must exist and be readable. Invalid entries, duplicate names and an unknown default configuration are reported as errors.

* Queries

~M-x org-files-db-query~ reads a structural query as an Emacs Lisp form, runs it and lets you select one result. The query language is described in the [[https://github.com/hubisan/org-files-db/blob/main/docs/reference/query-language.org][query language reference]]. A query starts with a target, one of ~headings~, ~files~ or ~links~, followed by conditions.

#+begin_src emacs-lisp
(org-files-db-query '(headings (tags "public")))
(org-files-db-query '(links (status "resolved")))
(org-files-db-query '(files))
#+end_src

The query can be a quoted form or a string. The command returns the selected result to Lisp callers. Keyword arguments:

- ~:config~: name from ~org-files-db-configs~ (default: ~org-files-db-default-config~)
- ~:columns~: columns to display
- ~:sort~: sort order
- ~:row-source~: row source
- ~:action~: function to call with the selected result instead of the default action

** Columns

Rust formats the result table, so the available column names are those of the [[https://github.com/hubisan/org-files-db/blob/main/docs/reference/presentation.org][presentation reference]]. A column is a list with the column name followed by options:

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 :columns '((todo-keyword :width (fixed 8))
            (outline-path :width (max 80))
            (file-name :width (max 30))))
#+end_src

- ~:width~ is ~auto~ (widest value), ~(max N)~ (automatic, capped at N) or ~(fixed N)~.
- ~:truncate~ is ~(:position left|middle|right :marker STRING)~ and controls how too long values are shortened.
- ~:separator~, ~:include-root~ and ~:include-match~ tune outline path columns such as ~outline-path~, ~source-outline-path~ and ~target-outline-path~.

Without ~:columns~, the defaults for the query target are used. Customize them with ~org-files-db-heading-columns~, ~org-files-db-file-columns~ and ~org-files-db-link-columns~.

** Sorting

~:sort~ is a list of columns, each optionally followed by ~:direction asc~ or ~:direction desc~. A sort column does not have to be displayed.

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 :sort '((priority :direction asc)
         (outline-path :direction asc)))
#+end_src

Without ~:sort~, the defaults ~org-files-db-heading-sort~, ~org-files-db-file-sort~ and ~org-files-db-link-sort~ apply (all ~nil~ by default, which keeps the order returned by ~orgfdb~). An explicit ~:sort nil~ keeps the ~orgfdb~ order even if a default is configured.

** Row sources

Normally each matching heading or file is one row. A row source turns each match into one row per entry of a list instead. Pass it as ~:row-source~ (a symbol or a string); it works for heading and file queries.

- ~tags~: one row per tag. ~* BJJ :sport:kampf:~ becomes two rows, one for ~sport~ and one for ~kampf~. Show the tag of each row with the ~tag~ column.
- ~effective-properties~: one row per property, including inherited ones. Show them with the ~property-name~ and ~property-value~ columns.
- ~keywords~: one row per file keyword such as ~#+title~. Show them with the ~keyword-name~ and ~keyword-value~ columns.

A match whose list is empty produces no row at all: with ~:row-source tags~, headings without tags disappear from the result. Every row still points to its heading or file, so actions open the same place.

#+begin_src emacs-lisp
(org-files-db-query '(headings (todo))
                    :row-source 'tags
                    :columns '((tag :width (max 20))
                               (outline-path :width (max 80))))
#+end_src

** Faces

Cells are shown with the faces of the ~org-files-db~ customization group (for example ~org-files-db-todo~, ~org-files-db-tag~ or ~org-files-db-file-name~). They inherit from the matching Org faces.

* Predefined views

A view is a named query with its own presentation and behaviour. Define views in ~org-files-db-views~ and run one with ~M-x org-files-db-view~, or ~(org-files-db-view "open-tasks")~ from Lisp.

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("open-tasks"
         :query (headings (not (done)))
         :columns ((todo-keyword :width (fixed 8))
                   (outline-path :width (max 80)))
         :sort ((priority :direction asc)
                (outline-path :direction asc)))
        ("work-links"
         :config "work"
         :query (links (status "resolved"))
         :action org-files-db-actions-open-link-target)
        ("all-headings"
         :query (headings)
         :cache t)))
#+end_src

A view is a name followed by these keys, each at most once:

- ~:query~ (required): the structural query
- ~:config~: configuration name (default: ~org-files-db-default-config~)
- ~:columns~, ~:sort~, ~:row-source~: same as for ~org-files-db-query~, with the same defaults
- ~:action~: action for this view, see [[*Result actions][Result actions]]
- ~:cache~: ~t~ to use the cache described below
- ~:display~: ~buffer~ to show the view in a result buffer instead of completion, see [[*Result buffer][Result buffer]]

View names must be unique. Invalid views are reported when they are validated.

** Cache

A view with ~:cache t~ is prepared by ~orgfdb~ and kept up to date, so large result sets open faster. This only takes effect while ~org-files-db-cache-mode~ is active. Without the mode every view simply runs as an ordinary query.

- ~M-x org-files-db-cache-start~ (or ~(org-files-db-cache-mode 1)~) prepares all views with ~:cache t~. Cache mode starts watch mode if it is not already active.
- ~M-x org-files-db-cache-stop~ (or ~(org-files-db-cache-mode -1)~) removes the prepared views. With a prefix argument it also stops watch mode.

Cache mode snapshots the view definitions when it starts. Restart it after changing ~org-files-db-views~, ~org-files-db-configs~ or the default configuration. Views prepared by Emacs are private to the running Emacs session and are removed when you stop cache mode or exit Emacs.

** Candidate cache

While ~org-files-db-cache-mode~ is active, Emacs also keeps the built completion candidates of every view with ~:cache t~ (one entry per view), so opening the same view again is instant: ~:cache t~ means the Emacs candidate cache plus the ~orgfdb~ prepared view. Views without ~:cache t~ and all views while the mode is off are never kept. The candidates are reused until the index changes, the view definition changes or the date changes; the index state is checked with one quick ~orgfdb status~ call. There is no size limit. Toggling ~org-files-db-cache-mode~ clears it. ~M-x org-files-db-cache-report~ lists the kept views with their rows, approximate memory, index generation and build time in ~*org-files-db cache*~.

** Watch mode

~orgfdb~ keeps the index current while a watcher process runs. ~org-files-db-watch-mode~ makes sure there is one for every configuration in ~org-files-db-configs~. A watcher that is already running outside Emacs is reused and left alone; watchers started by Emacs are stopped when you stop the mode or exit Emacs.

- ~M-x org-files-db-watch-start~ (or ~(org-files-db-watch-mode 1)~) starts the watchers.
- ~M-x org-files-db-watch-stop~ (or ~(org-files-db-watch-mode -1)~) stops those started by Emacs. It is refused while cache mode is active; stop cache mode first.

~org-files-db-watch-startup-timeout~ (default 60) is the number of seconds to wait for a watcher to become ready, or ~nil~ to wait without limit.

* Result actions

Selecting a result runs an action with that result. The default action depends on the query target:

- ~org-files-db-heading-action~ for ~headings~
- ~org-files-db-file-action~ for ~files~
- ~org-files-db-link-action~ for ~links~

All three default to ~org-files-db-actions-open-result~. A view overrides them with ~:action~, a single call with ~:action~ in ~org-files-db-query~. An action is any function that takes the selected result as its only argument.

Built-in actions:

- ~org-files-db-actions-open-result~ opens a heading, a file or the source of a link at its position.
- ~org-files-db-actions-open-link-target~ opens the target of a link result: a resolved target at the target heading or file, any other link (a web link, a directory, an unresolved file) as Org would open it from its source file.
- ~org-files-db-actions-follow-heading-link~ opens the first link found in a heading, in its headline first and then in its section, directly at its target (a file, a heading, or Dired for a directory). For a file result it uses the first link before the first heading. The heading's own buffer is not displayed and is closed again when it was not open before.
- ~org-files-db-actions-follow-or-open-heading~ follows a link in the headline itself, of any type, and otherwise opens the heading. It suits headings that are links, such as an index or path hierarchy of links to notes. With Embark it is on ~j~.
  A view that lists only headings with a link in the headline itself and follows that link (needs ~orgfdb~ with the ~source-context~ predicate):

  #+begin_src emacs-lisp
  (setq org-files-db-views
        '(("paths" :query (headings (has-link (links (source-context "heading"))))
                   :action org-files-db-actions-follow-or-open-heading)))
  #+end_src
- ~org-files-db-actions-insert-file-link~ inserts a ~file:~ link to a file result at point, relative to the current buffer when it visits a file.
- ~org-files-db-actions-insert-heading-link~ inserts a link to a heading result at point: an ~id:~ link if the heading has an ~ID~, else a file link with the ~CUSTOM_ID~. A heading with neither gets the file link with the heading title, or, when ~org-files-db-create-heading-id~ is ~custom-id~ or ~id~, a new ~CUSTOM_ID~ (from ~org-id-new~) or ~ID~ saved in its file and a link to it. For a file result it inserts a file link.
- ~org-files-db-actions-rename-file~ renames a file result and updates the ~file:~ links that point to it in other files. Links whose text no longer matches the index are skipped and counted in the message. The change spans several files and is not atomic, so use version control.

Actions that need more data than the list shows, such as the link and rename actions, ask ~orgfdb~ for it when you run them. If the files were indexed again since the result list was built, they stop with the message "Index changed, run the query again" and change nothing. Run the query again and select the result once more.

* Renaming or moving a directory

~M-x org-files-db-rename-directory~ renames a directory or moves it to another parent and updates the indexed ~file:~ links. It asks for the directory and the new path (a bare name stays in the same parent); a missing parent of the destination is created. With a prefix argument it asks for the configuration.

- In Dired the directory at point (or the current Dired directory on a file line) is the default source, and the Dired buffer showing the parent is reverted after the change.
- With Embark, ~M~ in the file action map (~embark-file-map~) runs ~org-files-db-embark-rename-directory~ on the directory at point or in the minibuffer and asks only for the destination. An existing ~M~ binding is kept.
- Incoming links from files outside the directory are rewritten, keeping their format, description, search option and relative or absolute form. Links to the directory itself are rewritten too. Relative links between files inside the directory stay unchanged unless they pass through the directory name (~../dir/file.org~), absolute ones inside it are rewritten.
- When moving to another parent, relative ~file:~ links in files inside the directory that point outside it are rewritten relative to the new location. Absolute links stay unchanged, and a pure rename leaves relative links as they are.
- The links come from ~orgfdb~ and are guarded by the index state, so a changed index stops with "Index changed, run the query again" before anything changes.
- The plan is shown in ~*org-files-db rename directory*~ like a diff: per file, each link with its line number, the old text as a removed and the new text as an added line, then the skipped links and nothing changes until you confirm. Links whose text no longer matches the index are skipped and counted in the message.
- The command refuses an existing destination, a destination inside the directory and modified buffers visiting an affected file or a file inside the directory. Buffers visiting files inside the directory follow the move.
- When a step fails, the edited files are restored, the directory is moved back, and the error lists anything that could not be undone. It does not check whether the directory is the root of a configured directory, so do not move a root.

~M-x org-files-db-undo-rename-directory~ undoes the last rename or move of the session: it restores the original text of the edited files and moves the directory back. It shows the files whose links it restores, asks for confirmation and refuses, changing nothing, when the new directory is gone, the old path exists again, an edited file changed since or a buffer visiting it is modified. It needs no ~orgfdb~ call; the record is forgotten after a successful undo.

* Result buffer

Instead of selecting one result in the minibuffer you can list every row in a read-only buffer.

- ~M-x org-files-db-show-view~ asks for a view and shows it in ~*org-files-db: NAME*~.
- ~M-x org-files-db-show-query~ reads a query like ~org-files-db-query~ and shows it in ~*org-files-db: query*~.
- ~(org-files-db-show-query QUERY &rest KEYS)~ takes the same keywords as ~org-files-db-query~ (~:config~, ~:columns~, ~:sort~, ~:row-source~, ~:action~). ~(org-files-db-show-view NAME)~ does the same for a view. Both return the buffer.
- A view with ~:display buffer~ is shown this way by ~org-files-db-view~ too. Only ~buffer~ and ~nil~ are valid.

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("Next" :query (headings (todo "NEXT")) :display buffer)))

(org-files-db-show-query '(headings (todo "NEXT")))
#+end_src

The buffer uses ~org-files-db-export-mode~ and does not need Embark. Each line is one row as the table shows it. In the buffer:

- ~RET~ runs the action of the view or call, else the default action for the result kind
- ~o~ exports the rows as an outline, see [[*Outline export][Outline export]]
- ~g~ runs the query again and keeps point on the same line number
- ~n~ and ~p~ move to the next and previous line

An empty result shows one line "No results". The buffer is reused when you show the same view or query again, and it is never refreshed automatically.

* Embark integration

Embark is optional and never required. Results complete in the ~org-files-db-result~ category. Once Embark is loaded, ~embark-act~ on a result offers ~org-files-db-embark-result-map~:

- ~o~ opens the result
- ~t~ opens the link target
- ~f~ inserts a file link
- ~h~ inserts a heading link
- ~l~ follows the first link in the heading
- ~j~ follows the link in the headline, or else opens the heading
- ~r~ renames the file

~embark-export~ lists the rows that match the current minibuffer filter, in the displayed order, in an ~*org-files-db export*~ buffer using ~org-files-db-export-mode~. In that buffer:

- ~RET~ runs the default action for the result on the current line
- ~n~ and ~p~ move to the next and previous line
- ~embark-act~ on a line offers the same actions as in the minibuffer
- ~o~ exports the rows as an outline, see below

** Outline export

~org-files-db-embark-export-outline~ exports heading results as an Org outline of links in a read-only ~*org-files-db outline*~ buffer. Run ~embark-export~ (~E~) on the results first, then press ~o~ in the ~*org-files-db export*~ buffer to turn its rows into the outline. Other result kinds are refused with "Outline export needs heading results". ~org-files-db-outline-export~ does the same from Lisp for a list of heading records and their presentation.

Every file becomes a top-level heading with a link to the file, and its headings sit one level deeper than in the file. Headlines keep the TODO keyword, priority and local tags (not inherited ones); the title is a link to the heading: ~file:PATH::#CUSTOM_ID~, else ~id:ID~, else ~file:PATH::LINE~. Matched headings are highlighted with the face ~org-files-db-outline-match~. ~C-x C-s~ in the buffer saves the text, without faces, to a file.

The structure comes from ~orgfdb~, the content is read from the source files. If the index no longer matches a file, the export stops with "Index changed, run the query again" and exports nothing.

- ~org-files-db-outline-export-ancestors~ (default ~t~) keeps the ancestors of matched headings. When ~nil~ only matched headings are listed, flat on level 2 under their file.
- ~org-files-db-outline-export-children~ (default ~nil~) adds the direct child headings (~children~) or all descendant headings (~subtree~) of matched headings as links.
- ~org-files-db-outline-export-planning~ (default ~t~) copies the planning line.
- ~org-files-db-outline-export-properties~ (default ~nil~) copies the property drawer of matched headings.
- ~org-files-db-outline-export-body~ (default ~nil~) copies the body text of matched headings.

Ancestors and added children only get their headline, and ancestors also their planning line, never properties or body.

* Development

#+begin_src shell
make setup
make ci
#+end_src

- ~make setup~ installs the development dependencies with [[https://emacs-eask.github.io/][Eask]].
- ~make ci~ runs the full check: package, install, byte-compilation, linting and Buttercup tests.
- ~make test~ runs only the Buttercup tests.
- ~make fmt~ formats the Emacs Lisp files.
- ~make bench~ runs the on-demand end-to-end benchmark against a real ~orgfdb~. The results are in [[file:docs/benchmark.org][docs/benchmark.org]].
