Emacs interface for [[https://github.com/hubisan/org-files-db][org-files-db]].  The package keeps indexing and SQLite access in the ~orgfdb~ executable and uses its JSON interfaces for queries and search.

* Requirements

- Emacs 29.4 or newer
- ~orgfdb~ installed or available through an explicit path
- [[https://github.com/jwiegley/emacs-async][async.el]] for background predefined-view cache refreshes
- [[https://github.com/minad/consult][Consult]] for live FTS5 search
- [[https://github.com/oantolin/embark][Embark]] for exporting the currently filtered completion candidates
- [[https://emacs-eask.github.io/][Eask]] for development

Consult and Embark are optional at runtime.  Ordinary queries, one-shot search, views, actions, and dynamic blocks work without them.  Pre-caching is disabled unless a predefined view opts in with ~:pre-cache t~.

* Configuration

#+begin_src emacs-lisp
(setq org-files-db-executable "orgfdb")
(setq org-files-db-config-file "~/org/org-files-db.toml")
#+end_src

Run ~M-x org-files-db-check-setup~ to inspect the resolved executable, configuration file, version, and read-only database access.

The global file is the default for every operation.  Query, search, live-search, action, setup-diagnostic, view, and dynamic-block entry points may override it for one invocation.  Omitting ~:config-file~ inherits the global value, a path selects another configuration, and an explicit ~nil~ invokes ~orgfdb~ without ~--config~.

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 nil
 nil
 :config-file "~/org/private/org-files-db.toml")

(org-files-db-query
 '(headings (tags "public"))
 nil
 nil
 :config-file nil)
#+end_src

Configuration paths are expanded and must identify readable files.  Relative paths are resolved against ~default-directory~ at invocation time.

* Query

~org-files-db-query~ accepts an ~orgfdb~ query expression as Emacs Lisp data:

#+begin_src emacs-lisp
(org-files-db-query
 '(headings (not (done)))
 '((todo-keyword :width (fixed 8))
   (priority :width auto)
   (outline-path :width (max 80))
   (file-name :width (max 30))))
#+end_src

The result list uses standard Emacs completion and therefore works with the default UI, Vertico, Icomplete, and Fido.  The selected result is opened at its stored UTF-8 byte location by default.

Supported column widths are:

- ~auto~: use the widest value in the current result set
- ~(max N)~: calculate automatically, capped at ~N~ columns
- ~(fixed N)~: always use ~N~ columns

Default columns can be customized separately for headings, files, links, and search results.

** Outline paths and truncation

Heading and search results use the ~outline-path~ column.  Link results use two explicit columns: ~source-outline-path~ is the hierarchy containing the link, while ~target-outline-path~ is the hierarchy of its resolved target.  Unresolved, ambiguous, external, unsupported, and structurally incomplete targets produce an empty target path rather than displaying the authored link target.

#+begin_src emacs-lisp
(setq org-files-db-outline-path-separator " » ")
(setq org-files-db-outline-path-include-root nil)
(setq org-files-db-outline-path-include-match t)

(org-files-db-query
 '(links (status "resolved"))
 '((source-outline-path
    :separator " » "
    :include-root nil
    :include-match t
    :width (max 50)
    :truncate (:position right :marker "…"))
   (link-description :width (max 40))
   (target-outline-path
    :separator " » "
    :include-root t
    :include-match t
    :width (max 50)
    :truncate (:position middle :marker "…"))
   (resolution-status :width (fixed 10))))
#+end_src

~:separator~ controls the text between components.  ~:include-root~ includes the corresponding source or target file title.  ~:include-match nil~ omits the final source heading or resolved target heading.  For a target that resolves directly to a file, ~target-outline-path~ is empty unless ~:include-root t~ is used.

The package infers required CLI includes from the configured columns.  ~source-outline-path~ requests source path context and ~target-outline-path~ requests structured target context; both are retrieved in the same flat query invocation.  Users do not need to add ~--include~ or switch to outline output.  For compatibility, ~outline-path~ on link results currently behaves like ~source-outline-path~, but new configurations should use the explicit link column name.

Truncation is available for every displayed column.  Customize the defaults with ~org-files-db-truncate-position~ and ~org-files-db-truncate-marker~, or override them per column with ~:truncate (:position left|middle|right :marker STRING)~.  The marker counts toward the final column width, and an empty marker performs hard truncation.

** Large result sets

Query and search presentation is eager and synchronous.  The package normalizes column definitions once, extracts each displayed value once per row, calculates shared widths from cached cell widths, sanitizes each distinct face once, and formats every completion candidate once.  Completion filtering and redisplay operate only on the prepared candidate strings; selected actions and Embark still receive the original result object.

Duplicate visible candidates retain separate invisible identities and direct result metadata.  Prepared CLI order is preserved, selection does not scan the complete candidate list, and values shortened for display remain available to completion filtering through hidden untruncated text.

For a real invocation, profile Emacs with ~M-x profiler-start~, run the query, and inspect ~M-x profiler-report~.  The development benchmark covers synthetic sets of 100, 1,000, 10,000, and 50,000 rows, representative inexpensive and expensive columns, and alist versus hash-table JSON parsing:

#+begin_src shell
emacs -Q -L lisp -l benchmarks/org-files-db-benchmark.el \
  --eval '(org-files-db-benchmark-run 3)'
#+end_src

Run ~M-x org-files-db-benchmark-query~ to separate real CLI execution, JSON parsing, result normalization, presentation, and total time for the current database.  Run ~M-x org-files-db-benchmark-compare-frontends~ interactively to compare initialization of standard completion and Consult using the same already prepared candidates.  Consult remains optional and normal query completion does not depend on it.

Run ~M-x org-files-db-benchmark-view-cache~ to compare synthetic cold preparation, warm cache lookup, compact worker-result transfer, main-process publication, a small affected-file patch, and a complete rebuild.

* Search

Perform one FTS5 search:

#+begin_src emacs-lisp
(org-files-db-search
 "title:sqlite AND body:index*"
 nil
 nil
 :scope 'all
 :config-file "~/work/org-files-db.toml")
#+end_src

Start Consult-powered live search with ~M-x org-files-db-search-live~.  Search starts after ~org-files-db-search-min-input~ characters, debounces changing input, and discards obsolete processes.

#+begin_src emacs-lisp
(org-files-db-search-live
 nil
 nil
 :scope 'title
 :config-file "~/work/org-files-db.toml")
#+end_src

The former leading positional search scope remains accepted for compatibility, including before ~:config-file~, but keyword arguments are preferred.

* Predefined views

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("open-tasks"
         :command query
         :config-file "~/org/private/org-files-db.toml"
         :query (headings (not (done)))
         :columns ((todo-keyword :width (fixed 8))
                   (outline-path :width (max 80))))
        ("project-search"
         :command search
         :expression "org-files-db"
         :scope title)
        ("resolved-links"
         :command query
         :query (links (status "resolved"))
         :columns ((source-outline-path :width (max 50))
                   (link-description :width (max 30))
                   (target-outline-path :width (max 50))))
        ("public-tasks"
         :command query
         :config-file nil
         :query (headings (tags "public")))))
#+end_src

Use ~M-x org-files-db-views-query~ or ~M-x org-files-db-views-search~.  From Lisp, pass the view name directly.

A view without ~:config-file~ inherits ~org-files-db-config-file~.  A path selects that configuration for the delegated query or search, while an explicit ~nil~ disables ~--config~ for the view.

** Generation-aware pre-caching

Pre-caching is an advanced opt-in feature for predefined views.  Add ~:pre-cache t~ to mark a view for caching, then enable the global cache mode:

#+begin_src emacs-lisp
(setq org-files-db-views
      '(("all-headings"
         :command query
         :pre-cache t
         :query (headings)
         :columns
         ((todo-keyword :width (max 10))
          (title :width (max 70))
          (file-name :width (max 30))))
        ("project-search"
         :command search
         :pre-cache t
         :expression "org-files-db"
         :scope title
         :columns
         ((title :width (max 70))
          (file-name :width (max 30))))))
#+end_src

#+begin_src emacs-lisp
(org-files-db-cache-mode 1)
#+end_src

Enabling ~org-files-db-cache-mode~ immediately queues every configured view marked with ~:pre-cache t~.  The work stays asynchronous and runs one cache worker at a time, so views can be warm before their first use.  If a view is invoked while its initial or generation refresh is still running, the command waits for that existing worker instead of starting the same expensive work synchronously.  Disabling the mode stops workers and monitoring and releases the in-memory caches.  With the mode disabled, ~:pre-cache t~ is only an opt-in marker and predefined views execute normally without caching.

The cache uses the stable ~database_id~ and committed ~generation~ reported by ~orgfdb status~.  A warm view with the same database identity and generation skips query or search execution, JSON parsing, row preparation, width calculation, and candidate formatting.  Direct calls to ~org-files-db-query~ and ~org-files-db-search~ remain uncached.

When the generation changes, ~orgfdb changes~ determines the refresh action.  Complete structural query views without limits, offsets, row expansion, or custom sorting can rerun only the authoritative ~upsert_files~ through ~--restrict-files-json -~ and remove rows owned by deleted files.  Search views and query views whose complete result semantics cannot be patched are rebuilt completely.  A patch remains one complete view cache; it is not an independent cache per file.

Cache replacements use ~async.el~, but the worker boundary is deliberately narrow.  The child Emacs executes ~orgfdb~ and parses its response.  A complete refresh returns only the result objects and resolved column definitions; a patch refresh returns only the restricted upsert results.  The main Emacs validates the unchanged patch source when needed, merges the complete result set, and runs the already optimized presentation builder once.  This avoids serializing duplicate rows, cells, widths, faces, and candidate strings merely to reconstruct them again in the parent.  Result payloads travel through short-lived job-owned files, while only a small validation and timing envelope crosses async.el's serialized process channel.  Publication occurs only after the database identity, target generation, cache key, view-definition token, and refresh token are checked again, so an obsolete worker cannot overwrite a newer entry.  Worker processes have a bounded watchdog, and interactive waiting continues servicing process output, sentinels, timers, and follow-up generations.  If an interactively requested view is queued behind other initial prewarm jobs, its latest refresh is moved to the front of the remaining queue.  Set ~org-files-db-cache-debug~ non-nil to log status, queue, worker, notification, publication, and timing events while diagnosing a cache lifecycle.

SQLite file notifications are the primary wake-up signal when ~orgfdb status~ exposes the canonical database path.  Optional fallback polling is controlled by ~org-files-db-views-pre-cache-poll-interval~: set it to a positive number of seconds, or to nil to disable polling.  Polling only checks configurations that do not currently have an active file-notify watcher.  Package-controlled source changes become visible only after the Rust watcher commits a new generation; until then, the existing prepared cache remains the exact view of the previous committed database generation and is reused instead of rerunning the same query synchronously.

A missing or stale cache never produces an empty or knowingly stale completion.  A missing cache without an active initial worker keeps the normal synchronous first-open path.  When a stale cache is already refreshing, or can start its generation refresh, opening the view waits for that async replacement instead of cancelling it and duplicating the expensive query and presentation work synchronously.  If the generation advances again while waiting, the command follows the next replacement.  A worker failure or timeout falls back to the complete synchronous path.  Use a prefix argument with ~org-files-db-views-query~ or ~org-files-db-views-search~ to force a complete fresh synchronous view and replace its cache.

Cache management commands are:

- ~org-files-db-views-refresh-cache~
- ~org-files-db-views-refresh-all-caches~
- ~org-files-db-views-clear-cache~
- ~org-files-db-views-clear-all-caches~

Refresh commands use ~async.el~ by default; a prefix argument requests a complete synchronous refresh.  Clearing a cache does not modify the Rust database or the view definition.

Prepared views retain original result objects and completion metadata, so actions, duplicate candidates, configured order, and Embark export behave like a fresh view.  Large caches consume memory.  Conservative limits are controlled by:

#+begin_src emacs-lisp
org-files-db-views-pre-cache-max-entries
org-files-db-views-pre-cache-max-results
org-files-db-views-pre-cache-max-total-results
org-files-db-views-pre-cache-poll-interval
#+end_src

An oversized view remains usable synchronously but is not retained automatically for the same definition and generation.  Cache entries are evicted in least-recently-used order.  Caches are in-memory only and are rebuilt after Emacs restarts.

* Embark export

Query and search candidates use the ~org-files-db-result~ completion category.  With Embark installed, ~embark-export~ creates an Org buffer containing exactly the candidates matching the current minibuffer filter.

Customize:

- ~org-files-db-export-layout~ to ~flat~ or ~outline~
- ~org-files-db-export-linked-heading-style~ to ~preserve~ or ~resolve~

~preserve~ keeps authored links embedded in heading titles.  ~resolve~ follows those links and displays the effective target title.

* Result actions

The optional action argument of ~org-files-db-query~ and ~org-files-db-search~ receives the selected result object.  Package-owned execution metadata may be attached for follow-up operations.

Built-in actions and wrappers include:

- ~org-files-db-actions-open-result~
- ~org-files-db-actions-follow-heading-link~
- ~org-files-db-actions-insert-file-link~
- ~org-files-db-actions-insert-heading-link~
- ~org-files-db-actions-query-insert-file-link~
- ~org-files-db-actions-query-insert-heading-link~
- ~org-files-db-actions-rename-file-result~

File links support normal ~file:~, ~id:~, and file-plus-~CUSTOM_ID~ styles.  Heading links support ~id:~, file-plus-~CUSTOM_ID~, and title-based file search links.  Missing IDs are created with Org APIs and saved before the link is inserted.

~org-files-db-actions-rename-file~ updates resolved path-based links before renaming the target.  It preserves descriptions and heading or custom-ID search options, but the multi-file operation is not globally atomic.  Version control is strongly recommended.

Query and search results retain the effective configuration that produced them.  Follow-up CLI operations, such as indexed ID resolution or link discovery during rename, continue to use that configuration even if the global option changes later.

* Backlinks

~M-x org-files-db-actions-backlinks~ is a convenience wrapper around a normal link query for the current file or heading.  The returned objects are the source links, so selecting one jumps to the original link location.

* Org dynamic blocks

The package registers these block types:

#+begin_src org
,#+BEGIN: org-files-db-query :query "(headings (not (done)))" :layout flat
,#+END:

,#+BEGIN: org-files-db-query :view "open-tasks" :layout outline
,#+END:

,#+BEGIN: org-files-db-search :expression "sqlite AND index*" :scope all :layout flat
,#+END:

,#+BEGIN: org-files-db-query :query "(headings (tags \"private\"))" :config-file "~/org/private/org-files-db.toml" :layout flat
,#+END:

,#+BEGIN: org-files-db-search :expression "public report" :config-file none :layout flat
,#+END:

,#+BEGIN: org-files-db-backlinks :scope heading :layout flat
,#+END:
#+end_src

Update a block with ~org-update-dblock~ or all blocks with ~org-update-all-dblocks~.  Generated entries link back to their indexed source locations.

Direct blocks inherit the global configuration when ~:config-file~ is absent.  A path overrides it, and the dedicated value ~none~ disables ~--config~.  Blocks using ~:view~ inherit the selected view's configuration and must not also specify ~:config-file~.

* API naming

Public names identify their owning module, while the two central operations stay concise:

#+begin_example
org-files-db-query             central query operation
org-files-db-search            central search operation
org-files-db-search-live       live search operation
org-files-db-actions-*         public result action
org-files-db-actions--*        private action helper
org-files-db-cache-*           cache module operation
org-files-db-cache--*          private cache helper
org-files-db-views-*           public view operation
org-files-db-views--*          private view helper
org-files-db-dblock-*          public dynamic-block insertion command
org-files-db-dblock--*         private dynamic-block helper
org-files-db-query--*          private query helper
org-files-db-search--*         private search helper
org-files-db-export-*          public export operation
org-files-db-export--*         private export helper
org-files-db-benchmark-*       public benchmark command
org-files-db-benchmark--*      private benchmark helper
org-files-db--*                shared core helper
#+end_example

Names containing a double hyphen are internal implementation details and are not supported as public API.
