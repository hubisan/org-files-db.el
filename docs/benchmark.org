#+TITLE: Emacs Path Benchmark
#+STARTUP: showall

* Purpose

This page records where time goes between ~M-x org-files-db-query~ and a usable candidate list with large result sets. It covers the one-shot path (~orgfdb query --format presentation-json~) and the cached path (~org-files-db-cache-mode~ with ~orgfdb view read~). Issues: #27 (measurement) and #39 (allocation reduction).

* Running

~make bench~ copies ~lisp/~ into a temporary directory, byte-compiles it and runs ~bench/org-files-db-bench.el~ against the compiled package, as an installed package runs. It sets ~gc-cons-percentage~ to 0.1, the interactive default (batch Emacs reports 1.0, which hides most GC work). It is not part of ~make ci~. It prints a message and exits normally when ~orgfdb~ is not found. Set ~ORGFDB~ to select the executable and ~ORGFDB_BENCH_SIZES~ (space separated) to override the sizes.

For each size the script generates a corpus in a temporary directory (about 500 headings per file, levels 1 to 4, todo keywords, tags, some body text), runs ~orgfdb rebuild~ and then measures both paths three times. The tables show the median. Both paths use the columns ~title~, ~tags~, ~file-name~ and ~outline-path~ and the query ~(headings)~.

* Setup

- Machine: Intel Xeon 2.1 GHz, 4 CPUs, 16 GB RAM, Linux (x86_64).
- Emacs 29.3, batch mode with ~-Q~, ~gc-cons-threshold~ 800000 and ~gc-cons-percentage~ 0.1.
- ~orgfdb~ 0.1.0, release build.
- Corpus: 100, 1000, 10000 and 50000 headings in 1, 2, 20 and 100 files.
- Payload (stdout of ~presentation-json~): 45097, 448248, 4647589 and 22878708 bytes.
- ~orgfdb rebuild~ takes 0.02, 0.05, 0.38 and 2.06 seconds.

* Phases

- *orgfdb*: ~orgfdb~ run with stdout discarded. For ~view read~ this is the Rust cache lookup plus writing to the discarded output.
- *process call*: ~org-files-db-process--call-raw~, wall time including process start, pipe transfer into an Emacs buffer and decoding to a string.
- *transfer*: process call minus orgfdb. It is the cost of moving the payload into Emacs.
- *JSON parse*: ~org-files-db-process--parse-json~ on the stdout string.
- *presentation decode*: ~org-files-db-presentation--decode~ on the parsed JSON.
- *candidate construction*: ~org-files-db-presentation--candidates~ on the decoded presentation.
- *time until completion usable*: the complete package entry point (~org-files-db-query~ or ~org-files-db-view~) from the call until ~completing-read~ is entered. ~completing-read~ is replaced by a stub that records the time and returns the first candidate, so interactive completion itself is not measured.
- The GC rows show the garbage collection time (~gc-elapsed~ delta) and number of collections inside the phase. Each phase row already includes its GC part.

* Profiling and optimization (#39)

The first measurement (#27) ran the package from the ~.el~ sources, so Emacs interpreted it. Interpreted, presentation decode took 2.3 s and candidate construction 3.3 s at 50000 rows. Byte-compiled code, which is what an installed package runs, is 2 to 4 times faster in these two phases (and the interpreted run hid the real GC share), so the benchmark now compiles the package first.

Measured on the byte-compiled baseline (10000 rows, seconds, ~gc-cons-percentage~ 0.1):

- Candidate construction (0.30 s, of which 0.26 s GC): per candidate one visible string was built from copies of every cell (~copy-sequence~ plus ~string-join~), a metadata plist was built, and three ~add-text-properties~ passes ran over the candidate. The garbage triggered about 8 collections per 10000 candidates because each one traverses the whole retained heap.
- Presentation decode (0.16 s, 0.10 s GC): one ~mapcar~ list plus ~vconcat~ per row, a ~vector-value~ call with an extra validation per cell field, and ~intern~ for every role.
- JSON parse (0.14 s): parse time is the same for alist, hash table and plist objects and for ~json-parse-buffer~ (0.10 to 0.12 s at 10000 rows, 0.5 to 0.6 s at 50000 rows). The cost is the C parser creating about 4.6 MB of strings, so nothing is changed there.

Changes:

- ~--visible-row~ concatenates the display texts once (~mapconcat~) and puts the faces on the result with ~put-text-property~, instead of copying and propertizing every segment. ~--search-row~ uses ~mapconcat~ and loops with ~while~.
- ~--candidate~ adds the properties in two passes (body with its display text, hidden identity suffix with the empty display) that share one metadata plist, instead of three passes.
- Rows and cells are decoded with preallocated vectors and without the intermediate list; cell fields are bounds-checked once per cell, and role symbols are interned once per schema role. All validation and error messages are unchanged.
- ~gc-cons-threshold~ is let-bound to 64 MB (never lowered) during the synchronous JSON parse, ~--decode~ and ~--candidates~. The values are restored by the ~let~. In batch mode this lowers decode plus candidates at 10000 rows from 0.32 s to 0.10 s because the default threshold of 800000 bytes causes a collection every few hundred rows while the retained heap keeps growing.

Candidate strings, text properties, display strings, search text, ordering, action records and errors are unchanged (the specs are the contract, and the candidates of the 10000 row payload were also compared before and after).

* Notes

- The phases are measured in separate runs, so their sum differs from the total by GC timing noise. The candidate construction phase at 50000 rows varies the most because its GC share depends on the heap left by earlier phases.
- The one-shot payload at 50000 rows (22.9 MB) is smaller than the 28.8 MB of the Rust baseline in #5 because the corpus generator and columns differ.
- The numbers are from one machine in batch mode. Interactive Emacs with a faster CPU will be quicker.
- The "usable" time includes the GC of the surrounding Emacs heap, which grows with the payload. The remaining 10 collections at 10000 rows come from the process output buffer, the stdout string and the parse, which run outside the 64 MB threshold of the decode phases.

* Conclusion

- *10000 rows are now clearly under one second.* One-shot 0.55 s and cached 0.44 s until completion is usable (interpreted baseline: 1.07 s and 1.04 s). The remaining time is spread over orgfdb (0.12 s one-shot), moving the payload into Emacs (0.12 to 0.13 s), JSON parsing (0.13 to 0.14 s), decode (0.08 s) and candidates (0.08 s). No single Emacs phase dominates any more.
- *At 50000 rows* the one-shot path takes 2.7 s and the cached path 1.7 s (from 6.1 s and 4.9 s). JSON parsing (0.6 s), transfer (0.3 to 0.4 s) and the orgfdb query (1.0 s one-shot) are now as large as decode and candidates together. Further gains need a smaller payload (Rust side, for example no padding in the transmitted ~display_text~) or a cache of decoded candidates; neither is part of this change.
- *An Emacs-side cache is still not justified.* The cached path saves only the orgfdb part because Emacs parses, decodes and builds candidates from the full payload every time; with these costs at 10000 rows that is below 0.3 s.
